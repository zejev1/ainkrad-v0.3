# Ainkrad collaboration rules

These rules apply to every future Ainkrad commit package.

1. The user owns normal code commits and pushes through SPCK. The assistant must not write code or release changes to GitHub unless the user explicitly authorizes that GitHub write in the current conversation. Documentation-only GitHub updates may be made only when the user explicitly requests them.
2. Read-only verification of GitHub and Vercel is allowed when requested.
3. Work on one user action at a time. Deliver prepared changes as a ZIP in the chat unless the user explicitly authorizes another delivery path.
4. Before asking the user to commit in SPCK, remind them to use `zejev1@users.noreply.github.com` as the Git email.
5. Ainkrad v0.3 does not use Convex.
6. Cardinal is the project core, but the world remains autonomous. Cardinal never receives a resident mind/action/identity writer.
7. All outside access to the world, including entry and world-clock control, goes through an independent gateway that Cardinal cannot reach.
8. During a normal commit build, pause twice for additions: once after diagnosis/design and once after implementation before packaging. Ask whether the user has noticed or imagined anything else. Wait 30 seconds; if there is no reply, continue automatically. If the user replies, incorporate the answer before continuing.
9. Do not repeatedly ask whether errors appeared. The user will report an error if one occurs.

10. Before every future Ainkrad release, perform a release audit before giving the user the ZIP: verify migration and continuity, protected resident autonomy, Cardinal/Gateway decision-to-effect causality, bounded storage growth, typecheck and tests. Do not label or recommend a package as final until this audit passes. SAO Alicization / Underworld is the primary reference for world design; Cardinal is Ainkrad's separate improved architecture.

11. Complete the entire authorized task, not a silently reduced subset. Before packaging, map every requested outcome to implemented behavior and evidence, including visual and physical behavior where relevant. Passing tests alone does not establish completeness. Carry unfinished requirements forward and state concrete blockers honestly; do not defer requested functionality to another release merely to finish a package sooner. The user will interrupt and report new problems when needed; incorporate those reports into the active task.

12. A functional object must participate in the actual world. A boat requires boarding, continuous water movement, landing or return, and consequences for its occupants and carried goods; a fishing bonus alone is not a boat implementation. For each requested capability, verify the complete chain from acquired knowledge and voluntary choice through materials/time and physical use to its observable result and save/reload continuity. Never replace a requested mechanism with a label, decoration, stat bonus or unconnected helper and call it complete.

13. For SPCK exports, verify both loose and packed main refs, the exact current remote main ancestry, a portable self-contained Git object database and a flat ZIP root. An archive audit cannot establish that a phone-side Push will succeed. If SPCK only reports a generic rejection, do not invent a cause or advise disabling protection/force-pushing; preserve the user's work and obtain the actual rejection detail.

14. Current priority: first develop the autonomous mortal world and its agents toward the Underworld/Alicization reference; work on Cardinal's own new capabilities follows that foundation. Books, bodies, materials, tools, homes, travel and occupations must affect lived behavior. Preserve personal history and independent choice; do not manufacture prosperity, professions or consent through Cardinal.

15. Пользовательский номер выпуска берётся из `package.json`; интерфейс не содержит собственной копии номера. Общее краткое имя искусственных разумных обитателей в UI — **Искры**; конкретные народы (люди, эльфы и т.д.) сохраняют свои названия. Технические идентификаторы сохранений ради UI-терминологии не менять.
16. Дальняя суша не создаётся от движения камеры или заранее. Cardinal может предложить её только по факту дальнего добровольного морского исследования; независимая граница мира защищает обследованное море, сушу и маршруты. Ни появление суши, ни её отображение не дают жителям готовых знаний и решений.

17. **Permanent performance invariant — never optimize by making the world live less.** No performance optimization may reduce or suppress residents' semantic opportunities per unit of world time, including ordinary decisions, physical movement, exploration, learning/teaching, social contact, family formation, intimacy/consent decisions, pregnancy/birth processing, occupations, adventures, trade, settlement development, or other autonomous life simply because population, world age, or simulation speed increased.
18. **Never buy performance by deleting lived history or knowledge.** Existing residents, generations, relationships, memories, maps, exploration records, learned knowledge/skills, family state, pregnancies, settlement state, resources, routes, Cardinal evidence, and other committed save data must survive migrations and optimizations. Bounded hot caches/projections may be rebuilt, but committed semantic evidence may not be silently discarded or ignored to make the engine faster.
19. Allowed performance work is computational: better algorithms/data structures, indexing, caching with correct invalidation, incremental recomputation, batching of equivalent commits/rendering, bounded presentation/log views, de-duplication, locality, and avoiding repeated work. If a proposed optimization changes what residents can actually do or how often they can do it in the same amount of world time, it is a simulation-rule change, not a performance optimization, and requires the user's explicit approval as a separate change.
20. Every future Ainkrad ZIP/release/commit package must preserve rules 17–19 and prove them with regression checks against the latest accepted checkpoint. At minimum compare a fixed save/seed over equal world time for action opportunities, exploration/mobility, learning, family/reproduction continuity, map/knowledge continuity, population/age/birth/death outcomes, and save/reload migration, alongside wall time/CPU/memory. A speedup that materially reduces autonomous life or loses accumulated data is a failed optimization and must not be shipped.

21. **Permanent Cardinal architecture — detachable conductor, never a life-support dependency.** Cardinal is a removable orchestration/research layer. The world engine and every system-agent domain must remain capable of normal autonomous operation while Cardinal is OFF, absent, disconnected, crashed, or physically removed from the host machine. No system agent may block, pause, wait for, or require Cardinal in order to keep its domain alive.
22. **Cardinal ON/OFF are explicit operating modes.** The product must support explicit `CARDINAL ON` and `CARDINAL OFF` commands/buttons. Turning Cardinal OFF detaches orchestration authority only; it must not stop the world, reset agents, discard state, or change resident autonomy. Unexpected physical removal/disconnection must fail closed to `CARDINAL OFFLINE` for Cardinal control while the world and system agents continue locally.
23. **System agents own continuous world operation; Cardinal only conducts them.** Weather, resources, ecology, monsters/dungeons, settlements/economy and future system domains execute through autonomous domain agents/runtimes resident with the world. Cardinal may observe, coordinate priorities, request bounded changes through defined contracts, evaluate failures, or replace a faulty implementation within the same authorized domain, but Cardinal must not become the direct tick-by-tick executor of those domains.
24. **Reconnection is synchronization, never rollback.** When Cardinal reconnects after an absence, it reads the current world state, agent states and audit/event history, reconstructs what happened while it was away, and resumes orchestration from the present. It may not restore an old Cardinal-era snapshot over the autonomous world's newer history merely because it was absent.
25. **Cardinal portability is required.** Cardinal's runtime/state may live on removable or separate hardware (for example a USB drive or another computer) while the world and system agents live on the simulation host. Removing that hardware must be a supported operating condition, not a crash scenario. World persistence must never depend on the physical presence of Cardinal storage.
26. **Cardinal is built to prove measurable added value, not to create dependency.** The primary research goal is to demonstrate that Cardinal can keep a multi-agent autonomous world safer, more stable, self-repairing and aligned with the original constitutional design while reducing or eliminating routine human intervention. `CARDINAL OFF` is the fair control condition. The autonomous control must never be intentionally weakened so Cardinal appears useful. If measurable benefit is not confirmed, record that honestly; do not redefine success after the fact.
27. **No hidden Cardinal dependency.** Tests for every system-agent integration must include autonomous execution with Cardinal absent, explicit OFF→world progression→ON resynchronization, abrupt Cardinal disappearance, and save/reload while Cardinal is absent. If removal of Cardinal freezes, corrupts, rolls back, or removes mandatory domain computation, the architecture is broken even if the Cardinal-ON path works.

28. **Permanent validation target — the Cardinal Torture Test.** A final Cardinal demonstration must deliberately inject failures: break or stall Weather Agent, corrupt part of another system-agent state, create bounded conflicts between authorized agents, disconnect Cardinal during recovery, let the world continue for years without it, reconnect Cardinal, and test whether it can diagnose what happened and restore healthy operation through allowed contracts without violating world constitution, resident autonomy, or committed history.
29. **The comparison must be fair and reproducible.** Cardinal ON and Cardinal OFF trials must start from the same accepted checkpoint/seed and receive the same fault injections where technically possible. Results must come from real audit/event evidence, not hand-authored summary text. Required metrics include fault detection, successful automatic recovery, safe isolation, unresolved faults, constitutional violations, human interventions, rollback/data loss, agent downtime, recovery time, world continuity, autonomous-life continuity, and compute cost.
30. **The world UI must contain a persistent bottom diagnostics/comparison screen.** This screen is a required product surface, not optional debug UI. It must show Cardinal status (`ONLINE`, `OFF`, `OFFLINE`), experiment/checkpoint identity, comparable `WITH CARDINAL` and `WITHOUT CARDINAL` results, failure/recovery timelines, system-agent health, constitutional violations, human interventions, recovery success, world-continuity indicators, and performance cost. Where paired runs are unavailable, the UI must clearly say so instead of inventing a comparison.
31. **Every future design must check against the Cardinal experiment.** Before changing Cardinal, Gateway, system agents, recovery, persistence, diagnostics, or performance architecture, explicitly verify that the change preserves the detachable-conductor model and does not make the final ON-vs-OFF comparison impossible, unfair, or cosmetic. The authoritative detailed protocol is `docs/CARDINAL_VALIDATION_PROTOCOL.md`.

32. **Exact release provenance.** A final SPCK ZIP must contain the same source, tests, package lock and build configuration that passed the full GitHub typecheck, Vitest suite and production build. Record the checked SHA and run ID; do not label a previous candidate as verified. Keep all new files, current main ancestry and one flat project root. Mobile SPCK is for import/commit/push, not for running the release test suite. Never move remote main or deploy merely to validate a candidate.

33. **Every future change must preserve performance.** Measure relevant wall time, CPU and memory against the accepted baseline on the same inputs and equal simulated time. Reuse unchanged derived data; invalidate caches only when actual dependencies change. Avoid serializing cache keys, copying results, scanning whole worlds, or rebuilding indexes per resident/frame when the result can be safely reused. Caches must be bounded and must not become save history. Add operation-count checks for repeated requests and dependency invalidation, not only noisy timing assertions. A demonstrated slowdown is a regression to fix, never an acceptable hidden cost of adding another agent. Record unmeasured scenarios honestly; no claim of zero cost on all devices from a local benchmark. Rules 17–20 remain mandatory: no fewer decisions, less life, removed history or altered physics to obtain speed.

34. **Strict separation: world functions are not Sparks.** Infrastructure/system agents own world functions only. Sparks are a separate structure living in that world; these agents receive no resident state or authority over bodies, minds, emotions, decisions, goals, identity, memory, knowledge, skills or relationships. Do not edit Spark implementations as part of system-agent work. Pass only narrow domain inputs and expose only domain outputs. Existing independent Spark mechanisms may experience the world's physical conditions; that is not permission for a world agent to inspect, steer or rewrite a Spark. Read-only comparison of isolated test-run outcomes checks preservation and grants no production access. Iskorka is a separate project and must not be inspected or changed without the user's explicit permission.

35. **Cardinal may conduct system agents from its first launch.** The owner removed the 200-year intervention delay in f14. Narrow contracts, independent gateways, evidence thresholds and protected Spark autonomy still apply at every age. Cardinal must never feed resources to Sparks: no resource_relief, habitat_support or resource-recovery subsidies through laws or catastrophe recovery, including legacy pending commands. Preserve past committed effects and records without replaying them. Natural finite-world recovery remains autonomous. ON/OFF persists; OFF detaches orchestration without stopping the world; ON resumes from the present. Unchanged health must not trigger repeated diagnosis, recomputation, journal writes or world copies. Unrelated 200-year biological/world rules are unchanged.

36. **Номер фикса и номер сборки обязательны для каждого выпуска с изменением кода.** Единственный источник — `package.json` (version и ainkrad.build); lockfile должен совпадать. Следующий выпуск обозначен 0.3.22.f12 / сборка 12 как новая точка отсчёта, а не реконструкция ненумерованных старых выпусков. Каждый следующий фикс увеличивает оба числа; используйте `npm run release:fix`. UI и `release.json` показывают версию, сборку и точный Git SHA. Проверка выпуска должна отклонять повторное использование номера при изменении кода. В журнале изменений указываются содержание, ограничения и проверенный предшествующий коммит; для отката используют конкретный SHA, а не приблизительную дату.

37. **Растительность должна опираться на проверяемые сведения о настоящих растениях.** Для каждого поддержанного вида хранить источник, проверенные экологические признаки и отдельно предположения/коэффициенты модели. Полный цикл включает пригодность участка, сезонность, почву и погоду, размножение, перенос семян/спор, конкуренцию, стресс и гибель, физическое влияние на землю, сохранение и объяснимую диагностику. Проверять всю цепочку в работающем мире. Не называть коэффициенты калибровки измеренными данными и не выдавать ограниченный каталог за всю флору Земли. Агент сверяется с версионированным локальным каталогом; доступ к внешним источникам проходит через независимый инструмент обновления и не становится условием жизни мира. Создание видовой модели разрешено пользователем как изменение правил экологии, но не даёт права менять Искры или сокращать их возможности.

38. **Погодная карта строится только по запросу при 1м = 1м.** Никаких фоновых пересчётов её сетки, canvas или кадров, в том числе при ускорении. Открытый снимок закрывается при переходе на ускорение; освобождаются его данные и буфер. География и жизнь не меняются от просмотра. Пауза — внешний контроль времени: останавливает продвижение мира и накопление догона, сохраняет подтверждённую историю, переживает перезагрузку и не даёт Кардиналу доступа к часам.

39. **Водный агент отвечает только за физическую воду.** Конечные запасы снега, почвы, грунта и поверхности связаны с региональной погодой, растениями и существующим водосбором. Все внутренние перемещения сохраняют объём; осадки, испарение и уход в море учитываются явно. Нельзя подменять засуху неисправностью, пополнять воду при restore или создании нового локального участка внутри уже рассчитанного бассейна. Источники USGS/FAO и коэффициенты модели разделены. Агент работает без Кардинала; повреждённые физические записи сохраняются и изолируются, а не заменяются выдуманным благополучием.

40. **Искры дорабатываются отдельно.** По решению владельца f14 не меняет устройство Искр и механизм придумывания названий местности. Перенос из отдельного проекта — самостоятельный будущий этап после стабилизации мира; не выполнять его попутно с системными агентами.
