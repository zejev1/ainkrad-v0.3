# Ainkrad collaboration rules

These rules apply to every future Ainkrad commit package.

1. The user alone commits and pushes to GitHub through SPCK. The assistant must never commit, push, upload, or otherwise write to GitHub.
2. Read-only verification of GitHub and Vercel is allowed when requested.
3. Work on one user action at a time. Deliver prepared changes as a ZIP in the chat; do not send the archive by email.
4. Before asking the user to commit in SPCK, remind them to use `zejev1@users.noreply.github.com` as the Git email.
5. Ainkrad v0.3 does not use Convex.
6. Cardinal is the project core, but the world remains autonomous. Cardinal never receives a resident mind/action/identity writer.
7. All outside access to the world, including entry and world-clock control, goes through an independent gateway that Cardinal cannot reach.
8. During a normal commit build, pause twice for additions: once after diagnosis/design and once after implementation before packaging. Ask whether the user has noticed or imagined anything else. Wait 30 seconds; if there is no reply, continue automatically. If the user replies, incorporate the answer before continuing.
9. Do not repeatedly ask whether errors appeared. The user will report an error if one occurs.

10. Before every future Ainkrad release, perform a release audit before giving the user the ZIP: verify migration and continuity, protected resident autonomy, Cardinal/Gateway decision-to-effect causality, bounded storage growth, typecheck and tests. Do not label or recommend a package as final until this audit passes. SAO Alicization / Underworld is the primary reference for world design; Cardinal is Ainkrad's separate improved architecture.

11. Complete the entire authorized task, not a silently reduced subset. Before packaging, map every requested outcome to implemented behavior and evidence, including visual and physical behavior where relevant. Passing tests alone does not establish completeness. Carry unfinished requirements forward and state concrete blockers honestly; do not defer requested functionality to another release merely to finish a package sooner. The user will interrupt and report new problems when needed; incorporate those reports into the active task.
